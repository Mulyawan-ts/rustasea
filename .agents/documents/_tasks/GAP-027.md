# [GAP-027] README Tech Stack and Feature Table Missing ADOPT Crates

### 1. Context & Analysis

- **Trigger**: 
`README.md` carries a Tech Stack table and a proposed directory tree that are meant to give a newcomer the architecture at a glance. Both predate the ADOPT adoption wave and omit crates that are now part of the umbrella, so the README understates the framework surface and hides the dependencies a user would inherit by enabling the corresponding features.

- **Observation**: 
The Tech Stack table at `README.md:193-215` (columns Layer, Crate, Rationale) lists the M0-M6 core stack only: tokio, axum/tower, sqlx, deadpool-redis, the migrator, validator, jsonwebtoken/argon2/tower-sessions, serde, config/dotenvy, clap/xtask, syn/quote, queue, cache, schedule, askama/minijinja, axum ws/SSE, reqwest, object_store, pgvector/AI, testcontainers, and rustfmt/clippy. It does not mention the adopted crates. The crate tree at `README.md:402-433` likewise lists only a subset of `crates/`.

The adopted crates and their underlying dependencies are verified in the tree. `rustasea-i18n` (translations, `Illuminate\Translation` analogue) depends on `serde_json` and `toml`. `rustasea-excel` (spreadsheet import/export) depends on `csv` plus optional `calamine` and `rust_xlsxwriter` behind the `xlsx` feature. `rustasea-image` (image pipeline) depends on the `image` crate. `rustasea-modules` (modular application layout) depends on `serde`, `toml`, and `toml_edit`. `rustasea-action` (single-responsibility actions) depends on `serde` and `serde_json`. `rustasea-google` (service account auth) depends on `jsonwebtoken` with the `use_pem` feature and `rsa`. `rustasea-storage` provides an SFTP disk via optional `russh` and `russh-sftp` behind the `sftp` feature. The umbrella `crates/rustasea/Cargo.toml` re-exports all of these, several behind optional features (`excel`, `image`, `action`, `google`, `modules`, `storage-sftp`).

- **Goal**: 
Update the Tech Stack table and the directory tree in `README.md` to include all adopted crates (`rustasea-i18n`, `rustasea-excel`, `rustasea-image`, `rustasea-modules`, `rustasea-action`, `rustasea-google`, and the `rustasea-storage` SFTP disk) and their underlying dependencies, noting which are gated behind optional umbrella features.

### 2. Step & Implementation

1. Add rows to the `README.md:193-215` Tech Stack table for each adopted crate: crate name, layer/feature, and the concrete dependency (for example `rustasea-excel` maps to `calamine`/`rust_xlsxwriter`; `rustasea-google` maps to `jsonwebtoken` + `rsa`; the SFTP disk maps to `russh`/`russh-sftp`).
2. Annotate each adopted crate with its umbrella feature name (`excel`, `image`, `action`, `google`, `modules`, `storage-sftp`, and i18n which is always enabled) so readers know how to turn it on.
3. Extend the `README.md:402-433` `crates/` tree to list the adopted crates and the remaining omitted crates, each with a short comment.
4. Cross-reference `GAP-022` so the tree and the canonical inventory agree on the full crate set after GAP-022 lands.
5. Verify each dependency claim against the crate's `Cargo.toml` before writing it.
