# [GAP-030] HTTP Client Idle Timeout Unenforced in Runtime Transport

### 1. Context & Analysis

- **Trigger**: 
The HTTP client exposes an idle-timeout setting that users can configure, and the documentation presents it as a supported capability, but the value is never applied to outbound requests. A user who sets an idle timeout expects stalled connections to be dropped; because the setting is inert, a hung connection can hold a request open until the total timeout fires, or indefinitely when no total timeout is set.

- **Observation**: 
`crates/rustasea-http/src/lib.rs:322` defines the `HttpClient` struct, and `:325` declares `pub idle_timeout: Option<std::time::Duration>`. `new()` initializes it to `None` at `:335`, and the builder method `idle_timeout(...)` at `:354-356` stores the value. The send path is `pub async fn send_with(...)` at `:405`. Inside `send_with`, only the total request timeout is applied to reqwest (`request.timeout(self.timeout)`), roughly at `:412`, before `client.execute` and the optional `throw` handling. The `idle_timeout` field is never read at runtime. An idle (inter-byte) timeout requires watching the response body stream, which `send_with` does not do, so the setting remains unenforced. Both `README.md:129` and `docs/milestones.md` record this as a known limitation ("the idle timeout is declared but unenforced").

- **Goal**: 
Either implement a body-streaming idle timeout watcher in the transport (so a stall between bytes aborts the request after `idle_timeout`), or formally document the known limitation and the route-level mitigation, and keep the documentation consistent with whichever path is chosen.

### 2. Step & Implementation

1. Decide the path: implement the idle-timeout watcher, or document the limitation as accepted. Record the decision in the task.
2. If implementing: wrap the response body stream so that each chunk resets a timer; if no chunk arrives within `idle_timeout`, abort the request with a distinct error variant. Wire this into `send_with` at `crates/rustasea-http/src/lib.rs:405` so both request and response phases honour the configured idle window, and surface a clear error when it fires.
3. If documenting: add a limitation note to the HTTP client documentation (module doc in `crates/rustasea-http/src/lib.rs` and the README HTTP section) explaining that only total timeout is enforced, and state the route-level mitigation (per-route total timeout configuration).
4. Reconcile the README and milestone statements for GAP-030. These are legitimately still open, so the wording should describe the real current behaviour rather than implying the feature works.
5. Add tests: if implemented, a test with a slow or stalled body asserts the idle timeout fires; if documented, a test asserts the total-timeout behaviour remains correct.
