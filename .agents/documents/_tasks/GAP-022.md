# [GAP-022] Workspace Crate Count and Manifest Drift

### 1. Context & Analysis

- **Trigger**: 
Three separate documents disagree with each other and with the mechanical workspace truth about how many crates the repository contains. `.agents/documents/application/modules/manifest.md:14` declares "21 crates under crates/ + xtask (22 workspace packages total)". `README.md:454-459` and `docs/milestones.md:35` declare "29 crates under crates/ + xtask (30 packages)". Neither number matches the actual expansion of the workspace `members` glob. The drift was previously parked under `GAP-021`, which closed without reconciling the numbers. Readers cannot tell which count is authoritative, and the directory tree in `README.md:402-433` only enumerates a subset of the real crates.

- **Observation**: 
The workspace manifest is the mechanical source of truth. `Cargo.toml:1-3` reads `[workspace] members = ["crates/*", "xtask"]` with `resolver = "2"`. The `crates/*` glob expands to 43 crate directories, verified by enumerating `crates/`: `cargo-rustasea`, `rustasea`, `rustasea-action`, `rustasea-activitylog`, `rustasea-ai`, `rustasea-app`, `rustasea-auth`, `rustasea-authlog`, `rustasea-broadcast`, `rustasea-cache`, `rustasea-cli`, `rustasea-config`, `rustasea-debugbar`, `rustasea-events`, `rustasea-excel`, `rustasea-foundation`, `rustasea-google`, `rustasea-http`, `rustasea-i18n`, `rustasea-image`, `rustasea-inertia`, `rustasea-inertia-adapters`, `rustasea-inertia-client`, `rustasea-jsonapi`, `rustasea-livewire`, `rustasea-logging`, `rustasea-macros`, `rustasea-mail`, `rustasea-modules`, `rustasea-mongo`, `rustasea-openapi`, `rustasea-orm`, `rustasea-queue`, `rustasea-queue-dashboard`, `rustasea-router`, `rustasea-scaffold`, `rustasea-schedule`, `rustasea-search`, `rustasea-storage`, `rustasea-testing`, `rustasea-timezone`, `rustasea-validation`, `rustasea-view`. Adding the single `xtask` member yields 44 workspace members (43 crates plus `xtask`), which is what `cargo metadata` reports. The historical `manifest.md:9-35` table lists only 21 framework crates and predates the ADOPT adoption wave (i18n, excel, image, google, modules, action, activitylog, authlog, openapi, debugbar, queue-dashboard, timezone, logging, mail, mongo, scaffold, inertia family, livewire). `docs/adr/ADR-0006.md:19` repeats the stale "21 crates under crates/ + xtask" count and explicitly defers to `manifest.md`.

- **Goal**: 
Synchronize `manifest.md`, `ADR-0006`, `README.md`, and `docs/milestones.md` to document the true 44-member workspace inventory (43 crates under `crates/` plus `xtask`), categorized by milestone M0-M6 and by ADOPT starter-kit adoption, or establish automated metadata derivation (for example a generated inventory from `cargo metadata`) so future drift cannot occur silently.

### 2. Step & Implementation

1. Establish the authoritative count mechanically: run `cargo metadata --no-deps --format-version 1` and extract `workspace_members`, then confirm 43 crate directories under `crates/` plus `xtask`.
2. Rewrite the canonical crate inventory table in `.agents/documents/application/modules/manifest.md` to enumerate all 43 crates plus `xtask`, each tagged with its milestone (M0-M6), kind (umbrella, framework, proc-macro, runnable app, dev tooling), and the owning module slug. Add an "adopted via ADOPT-XXX" column for the crates that landed through the ADOPT program.
3. Update `docs/adr/ADR-0006.md:19` so the inventory clarification cites the reconciled count and points to the regenerated manifest table; keep the boundary decision text unchanged.
4. Update `README.md:454-459` to state the reconciled 44-member count and remove the stale "29 crates" sentence; extend the `README.md:402-433` directory tree to list every crate with its milestone comment.
5. Update `docs/milestones.md:35` so the workspace-inventory note cites the reconciled count and drops the `GAP-021` reference.
6. Optional automation: add a `xtask` subcommand (for example `crates:check`) that derives the inventory from `cargo metadata` and fails when a checked-in document count diverges, or generates the inventory block between markers.
